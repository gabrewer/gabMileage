# Sprint 03 — Fuel Logging

> **Milestone 3 of 6** | Depends on: Sprint 02 (Garage & Vehicles)
> **Goal**: Users can log fill-ups with smart auto-calculation of the third fuel field, view fuel history with per-fill-up MPG, and edit or delete past entries. The fuel tab comes alive.

---

## User Stories

### US-3.1: User logs a fill-up
**As a** user, **I want to** record a fill-up by entering date, odometer, and any two of {gallons, total cost, price per gallon} **so that** I can track fuel usage without doing math.

### US-3.2: User views fuel history
**As a** user, **I want to** see all fill-ups for a vehicle in reverse chronological order **so that** I can review fuel spending and economy over time.

### US-3.3: User sees per-fill-up MPG
**As a** user, **I want to** see miles-per-gallon calculated for each fill-up (when possible) **so that** I can spot efficiency changes.

### US-3.4: User edits a fuel log
**As a** user, **I want to** correct a fuel log entry I made a mistake on **so that** my records stay accurate.

### US-3.5: User deletes a fuel log
**As a** user, **I want to** remove an incorrect fuel log **so that** it doesn't distort my data.

## Screen Descriptions

### Vehicle Detail — Fuel Tab (Populated)

**What the user sees:**
- **Tab bar**: "Fuel" tab active (highlighted underline)
- **"Log Fill-up" button**: top of tab content (right-aligned on desktop, full-width on mobile)
- **Fuel log list**: reverse chronological by fill-up date
  - Each entry is a compact card showing:
    - **Date** — formatted: "Mar 15, 2026"
    - **Odometer** — formatted with commas: "45,230 mi"
    - **Fuel summary line**: "12.5 gal · $42.50" (gallons + total cost)
    - **MPG badge**: "28.4 mpg" in a subtle pill/badge — only shown when calculable (see rules below)
    - **Partial fill indicator**: small "Partial" tag in muted style if flagged
    - **Notes indicator**: small 📝 icon if notes exist (notes visible on tap/expand or in edit view)
  - Each entry has a **"⋯" overflow menu** with "Edit" and "Delete"
  - **Mobile**: entries are full-width cards, stacked vertically
  - **Desktop**: entries in a single-column list, max-width ~700px

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: MPG is shown per fill-up (not as a running average) and only when a non-partial prior fill-up exists.
> **Why**: Per-fill-up MPG helps users spot anomalies ("why was that tank so bad?"). A running average smooths away useful signals. First fill-up can't show MPG because there's no prior odometer reading to calculate distance from.
> **Alternatives considered**: Running average, both per-fill and average, no MPG in v1
> **Confidence**: High

**MPG Calculation Rules:**
- **MPG** = (current odometer − prior odometer) / gallons of current fill-up
- **Suppressed when**: 
  - This is the first fill-up (no prior odometer to calculate distance)
  - This fill-up is marked as partial (inaccurate: partial gallons for full distance)
  - The prior fill-up was partial (inaccurate: full gallons but distance includes a partial tank)
- When suppressed, the MPG badge is simply not shown — no "N/A" or placeholder

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: MPG is suppressed (not shown at all) for partial fill-ups and the fill-up following a partial.
> **Why**: A partial fill produces misleading economy data. If you only pumped 5 gallons but drove 300 miles, the "MPG" would be wildly inflated. The fill-up AFTER a partial is also unreliable because the distance can't be cleanly attributed to gallons. Showing no number is better than showing a wrong number.
> **Alternatives considered**: Show with a warning asterisk, show as "~estimate"
> **Confidence**: High

  4. **Total Cost** — currency input (2 decimal places)

     - Displayed with "$" prefix

     - Label: *"This was a partial fill-up"*
  
  7. **Notes** — textarea, optional
     - Placeholder: *"Any notes? (optional)"*

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Gas station field is omitted from v1.
> **Why**: Every field adds friction to the 30-second target. Gas station doesn't enable any v1 feature (no analytics, no station comparison). It can be added later as an optional field if users request it. "Fast entry" is a core design principle — every field must earn its spot.
> **Alternatives considered**: Optional "More details" expandable section with gas station
> **Confidence**: High

## Interaction Details

### Auto-Calculation UX (Core Behavior)

This is the trickiest UX in the app. Here's the exact specification:

**Field state tracking**: Each of the three fuel fields (gallons, totalCost, pricePerGallon) has a state:
- `empty` — nothing entered
- `userEntered` — the user typed a value
- `calculated` — auto-filled by the system

**Calculation triggers on blur** (when a field loses focus), not on every keystroke.

**Rules:**
1. When exactly 2 fields are `userEntered`, calculate the third:
   - gallons × pricePerGallon = totalCost
   - totalCost / gallons = pricePerGallon
   - totalCost / pricePerGallon = gallons
2. The calculated field displays in a visually distinct style: lighter text color + small "calc" pill
3. If the user manually edits the calculated field, it becomes `userEntered`. The oldest untouched `userEntered` field becomes the new calculated field (LIFO: the field the user hasn't touched most recently clears and recalculates)
4. If all three are manually entered and mathematically consistent (within $0.01 rounding): all show as `userEntered`, no "calc" label
5. If all three are manually entered and **inconsistent**: show a gentle inline note below the fields: *"These numbers don't quite add up — we'll use gallons and total cost to recalculate price/gal."* Priority: gallons + totalCost → recalculate pricePerGallon.
6. If only 0 or 1 fields are filled: no calculation, remaining fields stay empty
7. Clearing a `userEntered` field: re-evaluate. If only one `userEntered` field remains, clear the `calculated` field too.

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Auto-calculation fires on blur, not on keystroke.
> **Why**: Calculating on every keystroke causes flicker — type "3", see a result, type "3.", it changes, type "3.5", it changes again. On blur, the calculation fires once when the user moves to the next field. Calmer, less error-prone.
> **Alternatives considered**: Debounced keystroke (250ms), explicit "Calculate" button
> **Confidence**: High

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: When all three are manually entered inconsistently, we prioritize gallons + totalCost → recalculate pricePerGallon.
> **Why**: Users are most likely to know exact gallons (from the pump display) and total cost (from the receipt). Price/gal is the one most often rounded or misremembered. Using the two most reliable inputs is the safest default.
> **Alternatives considered**: Error forcing user to fix, use the most-recently-entered pair
> **Confidence**: Medium — reasonable default, but the warning should be visible enough.

### Log Fill-up Flow
1. User navigates to vehicle detail → Fuel tab
2. Taps "Log Fill-up" → navigates to fill-up form page
3. Date defaults to today; user can change it
4. Enters odometer (required)
5. Enters any two fuel fields → third auto-calculates on blur
6. Optionally toggles partial fill and/or writes notes
7. Taps "Save Fill-up" → spinner → success → navigate back to fuel tab
8. New entry appears in chronological position in the list
9. Toast: *"Fill-up logged!"*

### Edit Flow
1. User taps "⋯" on a fuel log → selects "Edit"
2. Navigates to edit form (pre-populated)
3. Modifies fields → "Save Changes"
4. Success: navigate back to fuel tab. Toast: *"Fill-up updated"*

### Delete Flow
1. User taps "⋯" on a fuel log → selects "Delete"
2. **Confirmation dialog**: *"Delete this fill-up from Mar 15, 2026?"* — "Delete" (red) + "Cancel"
3. Confirm: entry removed from list. Toast: *"Fill-up deleted"*
4. MPG for adjacent entries recalculates (or suppresses if the calculation baseline changed)

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Delete uses a confirmation dialog, not an undo toast.
> **Why**: Fill-ups contain odometer readings that feed MPG calculations and maintenance status. Accidental deletion cascades to other data. A confirmation dialog is safer for destructive actions on data with downstream effects.
> **Alternatives considered**: Undo-snackbar (5 seconds), no confirmation
> **Confidence**: High

### Validation Rules

| Field | Required | Validation | Error Message |
|-------|----------|------------|---------------|
| Date | Yes | Valid date, not in the future | *"Date can't be in the future"* |
| Odometer | Yes | Positive integer, max 9,999,999 | *"Enter a valid odometer reading"* |
| Gallons | Conditional | Positive number, ≤3 decimals, max 999.999 | *"Enter a valid amount"* |
| Total Cost | Conditional | Positive number, ≤2 decimals, max 9,999.99 | *"Enter a valid amount"* |
| Price/Gal | Conditional | Positive number, ≤3 decimals, max 99.999 | *"Enter a valid price"* |
| Notes | No | Max 500 characters | *"Notes are too long"* |

**Conditional rule**: At least two of {gallons, totalCost, pricePerGallon} must be filled on submit.
Error if fewer: *"Enter at least two fuel fields — we'll calculate the third."*

### Odometer Validation
- If the entered odometer is **lower than** the most recent prior reading: show a **warning** (not error): *"This reading is lower than your last one (44,800 mi). Double-check?"* — allow saving anyway. Reasons: odometer rollover, correction, backdated entry for an earlier date.
- If backdated: the odometer just needs to be internally consistent within the chronological sequence. The API stores it; projections sort by date.

### Loading & Error States
- **Fuel tab list**: 3 skeleton card placeholders
- **Fill-up form**: no loading (new form). Edit form: brief skeleton while existing data loads.
- **Save failure**: inline banner *"Couldn't save your fill-up — please try again."* Form re-enables.
- **Delete failure**: toast *"Couldn't delete — please try again."*
- **Tab load failure**: inline error with "Retry"

## Edge Cases & Decisions

### Decision: Miles or kilometers?
**Decision**: Miles only for v1. No unit toggle or conversion.
**Why**: Implicit US user base per PRD. Adding unit selection is UI complexity with no core benefit for the target user.
**Confidence**: Medium — revisit for international expansion.

### Decision: Fuel log sort order
**Decision**: Reverse chronological by fill-up date (not entry creation date). Same-date ties broken by odometer descending.
**Confidence**: High.

### Decision: What happens when a fill-up used for MPG is deleted?
**Decision**: MPG for adjacent entries recalculates. If the prior fill-up is deleted, the next entry's MPG uses the new prior entry (or suppresses if no prior remains).
**Confidence**: High.

### Decision: Fuel logs and maintenance are independent
A user can log fill-ups without ever defining maintenance items. Fuel logs establish odometer readings that maintenance (Sprint 04) can later use.
**Confidence**: High.

### Edge case: $0.00 total cost
Allowed — free fuel (employee perk, promotional, gift card). Price/gal would calculate to $0.000.

### Edge case: Extremely high odometer (>999,999 mi)
Allow up to 9,999,999 (7 digits). Validation accepts this. Display formats with commas.

### Edge case: All three fuel fields manually entered with matching math
All three are `userEntered`. No "calc" label shown. This is fine — the system just doesn't need to intervene.

### Edge case: User enters fuel data but no notes, then later wants to add notes
They edit the fill-up and add notes. The edit flow supports this.

## Data Contracts

### FuelLog (read model — API → Frontend)
```
FuelLog {
  fuelLogId: string (UUID)
  vehicleId: string (UUID)
  date: LocalDate                 // NodaTime
  odometer: number                // integer, miles
  gallons: number | null          // up to 3 decimal places
  totalCost: number | null        // up to 2 decimal places
  pricePerGallon: number | null   // up to 3 decimal places
  calculatedField: "gallons" | "totalCost" | "pricePerGallon" | null
  isPartialFillUp: boolean
  notes: string | null
  mpg: number | null              // server-calculated; null if can't compute
  createdAt: Instant
}
```

### FuelLogList (API → Frontend)
```
FuelLogList {
  vehicleId: string
  logs: FuelLog[]                 // sorted by date desc, then odometer desc
  lastOdometer: number | null     // most recent odometer reading for form helper
}
```
