# Sprint 03 — Fuel Logging

> **Milestone 3 of 6** | Depends on: Sprint 02 (Garage & Vehicles)
> **Goal**: Users can log fill-ups for their vehicles, view fuel history, and edit or delete past entries. The auto-calculated third field makes data entry fast.

---

## User Stories

### US-3.1: User logs a fill-up
**As a** user, **I want to** record a fill-up by entering just the date, odometer, and two of three fuel fields **so that** tracking is fast and I don't have to do math.

### US-3.2: User views fuel history
**As a** user, **I want to** see all my fill-ups for a vehicle in reverse chronological order **so that** I can review my fuel spending and economy.

### US-3.3: User edits a fuel log
**As a** user, **I want to** correct a fuel log if I made a mistake **so that** my records stay accurate.

### US-3.4: User deletes a fuel log
**As a** user, **I want to** remove an incorrect fuel log **so that** it doesn't skew my data.

### US-3.5: User sees fuel economy
**As a** user, **I want to** see miles-per-gallon for each fill-up **so that** I can track my vehicle's efficiency over time.

---

## Screen Descriptions

### Vehicle Detail — Fuel Tab (With Data)

**What the user sees:**
- Tab bar: "Fuel" tab is active (highlighted)
- **"Log Fill-up" button** at the top of the tab content (right-aligned on desktop, full-width on mobile)
- **Fuel log list**: reverse chronological
  - Each entry is a card/row showing:
    - **Date** (formatted: "Mar 15, 2026")
    - **Odometer** (formatted with commas: "45,230 mi")
    - **Gallons** and **Total cost** (e.g., "12.5 gal • $42.50")
    - **MPG** (calculated from the distance since last fill-up ÷ gallons) — shown only if there's a prior fill-up to calculate from. Displayed as "28.4 mpg" in a subtle badge.
    - **Partial fill** indicator: a small "Partial" tag if flagged
  - Each entry has a "•••" overflow menu (or swipe on mobile) with "Edit" and "Delete"
- **If no fill-ups**: empty state (from Sprint 02) with the "Log Fill-up" button now enabled

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: MPG is shown per-fill-up, not as a running average. It's only shown when a prior fill-up exists to calculate distance from.
> **Why**: Per-fill-up MPG is more useful for spotting changes ("why was that fill-up so bad?"). A running average smooths out useful signals. The first fill-up can't show MPG because there's no prior odometer to calculate distance.
> **Alternatives considered**: Running average MPG, both per-fill and average, no MPG display
> **Confidence**: High

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: MPG calculation skips partial fill-ups — a partial fill produces inaccurate economy data.
> **Why**: If you only put in 5 gallons but drove 300 miles, the "MPG" would be wildly inflated. The MPG for the fill-up AFTER a partial should also be suppressed (or noted as approximate) since the distance can't be accurately attributed to gallons.
> **Alternatives considered**: Show MPG with a warning label, always calculate regardless
> **Confidence**: High

### Log Fill-up Form (Full Page)

**What the user sees:**
- **Page title**: "Log Fill-up" with back arrow → returns to vehicle detail / fuel tab
- **Vehicle name** shown below the title as context (e.g., "for Blue Thunder")
- Form fields:
  1. **Date** — date picker, defaults to today, fully editable for retroactive entry. No future dates allowed.
  2. **Odometer** — numeric input, required. Placeholder: *"Current odometer reading"*. Shows the last recorded odometer below as helper text: *"Last reading: 44,800 mi"* (or *"No prior reading"* if first entry).
  3. **Gallons** — numeric input (decimal allowed, up to 3 decimal places). Placeholder: *"Gallons"*
  4. **Total Cost** — currency input (2 decimal places). Placeholder: *"Total cost"*. Displayed with "$" prefix.
  5. **Price per Gallon** — currency input (3 decimal places, gas prices use 9/10ths). Placeholder: *"Price/gal"*. Displayed with "$" prefix.
  6. **Partial fill-up** — toggle/checkbox. Default: off. Label: *"This was a partial fill-up"*
  7. **Notes** — text area, optional. Placeholder: *"Any notes? (optional)"*. Max 500 characters.

- **Auto-calculation behavior**:
  - The three fuel fields (gallons, total cost, price/gal) are all editable
  - When exactly two are filled, the third auto-calculates and displays in a visually distinct style (lighter color, italic, or a small "calculated" label)
  - If the user manually edits the auto-calculated field, the most recently untouched field clears and becomes the new calculated field
  - If all three are manually entered and they're inconsistent, show a gentle warning: *"These numbers don't quite add up — we'll use gallons and total cost to calculate price/gal."* Priority: gallons + total cost → price/gal is recalculated.
  - If only one or zero fields are filled, no calculation happens — the other fields remain empty

- **Save button**: "Save Fill-up" — full-width on mobile, right-aligned on desktop
- **Gas station field**: NOT in v1 (PRD lists it as optional, deferring to keep the form fast)

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: When all three fuel fields are manually entered and inconsistent, we prioritize gallons + total cost and recalculate price/gal.
> **Why**: Users are most likely to know exactly how many gallons they pumped and the total on the receipt. Price/gal is the one most often rounded or misremembered. Using the two most reliable inputs to derive the third is the safest default.
> **Alternatives considered**: Show an error and force the user to fix it, use whatever was entered last
> **Confidence**: Medium — this is a reasonable default, but the warning should be clear enough that the user can correct it.

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Gas station field is omitted from v1 even though the PRD lists it as optional.
> **Why**: Every field adds friction. Gas station is nice-to-have but doesn't enable any v1 feature. Fast entry is a core principle — earn every field.
> **Alternatives considered**: Include as a collapsible "More details" section
> **Confidence**: High

### Edit Fuel Log Form

**What the user sees:**
- Same layout as "Log Fill-up" but:
  - Title: "Edit Fill-up"
  - All fields pre-populated with existing data
  - The auto-calculated field is indicated
  - Save button: "Save Changes"
  - A "Delete" link at the bottom of the form (red text, not a button — deliberate understatement to avoid accidental deletes)

## Interaction Details

### Log Fill-up Flow
1. User navigates to vehicle detail → Fuel tab
2. Taps "Log Fill-up" → navigates to the fill-up form
3. Date defaults to today. User can change it.
4. User enters odometer (required)
5. User enters any two fuel fields → third auto-calculates
6. Optionally toggles partial fill-up and/or adds notes
7. Taps "Save Fill-up" → spinner → success → navigate back to fuel tab
8. New entry appears at the top of the list (or in chronological position if backdated)
9. Toast: *"Fill-up logged!"*

### Edit Flow
1. User taps "•••" on a fuel log entry → selects "Edit"
2. Navigates to edit form (pre-populated)
3. User modifies fields → "Save Changes"
4. On success: navigate back to fuel tab, toast: *"Fill-up updated"*

### Delete Flow
1. User taps "•••" on a fuel log entry → selects "Delete"
2. **Confirmation dialog**: *"Delete this fill-up from Mar 15, 2026?"* with "Delete" (red) and "Cancel" buttons
3. On confirm: entry removed from list, toast: *"Fill-up deleted"*
4. No undo (event sourcing preserves the audit trail internally, but the user can't undo)

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Delete requires confirmation via a dialog, not an undo toast.
> **Why**: Fill-up data has odometer readings that feed into MPG calculations and maintenance tracking. Accidental deletion could cascade — safer to confirm than to rely on undo-within-a-window.
> **Alternatives considered**: Undo toast (Snackbar with "Undo" action), no confirmation
> **Confidence**: High

### Auto-Calculation UX Detail
- **Tracking which fields are "user-entered"**: maintain a state for each of the three fields: `userEntered` or `calculated`.
- When the user types in a field, mark it as `userEntered`.
- When exactly two fields are `userEntered`, calculate the third:
  - gallons × price/gal = total cost
  - total cost / gallons = price/gal
  - total cost / price/gal = gallons
- The calculated field is displayed with a subtle visual distinction (lighter text color + small "calc" label)
- If the user clears a `userEntered` field, re-evaluate: if only one field remains `userEntered`, clear the calculated field too.
- Calculation updates **on blur** (not on every keystroke) to avoid flickering while typing.

**UX Breadcrumb:**
> **Who**: product-designer
> **What**: Auto-calculation triggers on blur (field loses focus), not on every keystroke.
> **Why**: Calculating on every keystroke causes distracting flickering — the user types "3" and sees a result, then types "3." and it changes, then "3.5" and it changes again. On blur, the calculation happens once when the user moves on, which is calmer and more reliable.
> **Alternatives considered**: Keystroke-based (debounced), explicit "Calculate" button
> **Confidence**: High

### Form Validation Rules
| Field | Required | Validation | Error Message |
|-------|----------|------------|---------------|
| Date | Yes | Not in the future, valid date | "Date can't be in the future" |
| Odometer | Yes | Positive number, no decimals | "Enter a valid odometer reading" |
| Gallons | Conditional | Positive number, ≤ 3 decimal places, max 999.999 | "Enter a valid amount" |
| Total Cost | Conditional | Positive number, ≤ 2 decimal places, max 9999.99 | "Enter a valid amount" |
| Price/Gal | Conditional | Positive number, ≤ 3 decimal places, max 99.999 | "Enter a valid price" |
| Notes | No | Max 500 characters | "Notes are too long" |

**Conditional**: at least two of {gallons, total cost, price/gal} must be filled.
If fewer than two are provided on submit: *"Please enter at least two fuel fields — we'll calculate the third."*

### Odometer Validation
- If the entered odometer is **less than** the most recent prior reading for this vehicle: show warning (not error): *"This reading is lower than your last one (44,800 mi). Is that correct?"* — allow saving anyway (odometer rollover, correction, or retroactive entry with an older date).
- If the entry is backdated and the odometer falls between two existing readings, that's fine — it slots in chronologically.

### Loading States
- Fuel tab list: skeleton rows (3 placeholder rows)
- Fill-up form: no loading state needed (it's a new form)
- Edit form: brief skeleton while loading the existing entry data

### Error States
- Save failure: inline error banner *"Couldn't save your fill-up — please try again."*
- Delete failure: toast *"Couldn't delete — please try again."*
- Load failure on fuel tab: inline error with retry

## Edge Cases & Decisions

### Decision: Odometer — miles or kilometers?
**Decision**: Miles only for v1. No unit selection or conversion.
**Why**: The target user (from the PRD) is implicitly US-based. Adding unit selection adds UI complexity without serving the core user.
**Confidence**: Medium — this should be revisited if there's international interest.

### Decision: Fuel log sort order
**Decision**: Reverse chronological by the fill-up date (not by the date the entry was created). If two entries have the same date, sort by odometer descending.
**Confidence**: High.

### Decision: Can a user log a fill-up before adding an odometer reading for maintenance?
**Decision**: Yes. Fuel logs and maintenance are independent. The first fuel log establishes the first odometer reading.
**Confidence**: High.

### Decision: What if a fill-up is deleted and it was used for MPG calculation?
**Decision**: MPG for adjacent entries is recalculated. If the prior fill-up is deleted, the next entry's MPG is recalculated using the new prior entry (or suppressed if there's no longer a prior).
**Confidence**: High.

### Edge case: User enters $0.00 for total cost
Allow it — free fuel (employee perk, gift card) is a valid scenario. The calculated price/gal would be $0.000.

### Edge case: Extremely high odometer (> 999,999)
Allow up to 9,999,999 miles. Validation accepts up to 7 digits.

### Edge case: User enters all three fuel fields with matching math
All three are marked as `userEntered`. The calculated label is not shown. This is fine.

## Data Contracts

### FuelLog (read model — API → Frontend)
```
FuelLog {
  fuelLogId: string (UUID)
  vehicleId: string (UUID)
  date: LocalDate               // NodaTime
  odometer: number              // integer, miles
  gallons: number | null        // up to 3 decimal places
  totalCost: number | null      // up to 2 decimal places
  pricePerGallon: number | null // up to 3 decimal places
  calculatedField: "gallons" | "totalCost" | "pricePerGallon" | null
  isPartialFillUp: boolean
  notes: string | null
  mpg: number | null            // calculated server-side, null if can't compute
  createdAt: Instant
}
```

### FuelLogList (API → Frontend)
```
FuelLogList {
  vehicleId: string
  logs: FuelLog[]               // sorted by date desc, then odometer desc
  lastOdometer: number | null   // most recent odometer reading (for form helper text)
}
```
